# CLAUDE.md — правила работы над проектом

Проект пишется по плану из [PLAN.md](PLAN.md). **План — источник истины.** Не добавлять протоколы и
функции, которых там нет, и не менять принятые решения: Python stdlib + SQLite, один системный
пользователь `webproxy`, шарды по 16 слотов, секретный путь панели, бот с ручным/автоодобрением.
Технические уточнения к плану — в [docs/FINDINGS.md](docs/FINDINGS.md), сценарии проверки на
сервере — в [docs/TESTING.md](docs/TESTING.md).

Если в плане есть противоречие или пробел, влияющий на поведение для пользователя, — спросить владельца.
Технические мелочи решать самостоятельно и записывать в docs/FINDINGS.md.

После каждого этапа контекст очищается: всё нужное для продолжения должно быть в CLAUDE.md,
PLAN.md и docs/.

- GitHub: https://github.com/barakov-dot/tg-proxy-panel-v2, remote `origin`, ветка `main`.
  Доступ сохранён в связке ключей macOS.

## Среда разработки (macOS) — ВАЖНО

Код выполняется только на Ubuntu 22.04+/Debian 12+, установка на сервер — с GitHub.

На Mac **запрещено**:
- устанавливать что-либо: brew, pip, npm, go, docker-образы, любые пакеты и утилиты;
- использовать sudo и менять что-либо вне папки проекта (включая глобальный git config);
- запускать install.sh, update.sh, uninstall.sh, wppctl, systemd-юниты, nft и любые скрипты,
  рассчитанные на сервер (включая `tools/verify/*.sh`);
- git push --force, переписывание истории, удаление веток и тегов на origin.

На Mac **разрешено**:
- создавать и редактировать файлы в папке проекта;
- git add, commit, tag, push в origin main и push тегов;
- git clone в `./reference/` (только чтение исходников);
- запускать имеющийся `python3` для unit-тестов: `python3 -m unittest`;
- `bash -n` для проверки синтаксиса shell-скриптов.

Если чего-то для проверки нет на Mac, не искать способ это установить: написать, что проверка
переносится на сервер, и добавить её в docs/TESTING.md.

`reference/` (в .gitignore): `tproxy-server` @ `acc252ece3a25c29e9b83f608499a5567a33ab2a`,
`MTProxy` @ `f36d8af769ffaeac36978d38c2c0f6d1104c2137`. Если каталога нет — склонировать заново на этих коммитах.

## Требования к коду

- Совместимость с Python 3.10 (Ubuntu 22.04). Системный python3 на Mac может быть 3.9, поэтому
  не использовать синтаксис новее 3.9 (`match`, `X | Y` в аннотациях без
  `from __future__ import annotations`).
- `hashlib.scrypt` может отсутствовать в python на Mac (LibreSSL): такие тесты пропускать через
  `unittest.skipUnless`.
- Тесты не трогают /etc, /var, /opt, systemd, nft, сеть. Все пути берутся из конфигурации и в тестах
  указывают во временные каталоги. Всё системное изолировано в `system.py` и `ctl.py` и в тестах
  подменяется фиктивной реализацией.
- Никакого кода, зависящего от macOS.
- Shell-скрипты: `#!/usr/bin/env bash`, рассчитаны на bash 5. Локально только `bash -n`.
- `.gitattributes`: `* text=auto eol=lf` и явный `eol=lf` для `*.sh`, `*.py`, `*.service`, `*.timer`.
- Исполняемые файлы (install.sh, update.sh, uninstall.sh, tools/verify/*.sh, ctl) — бит через
  `git update-index --chmod=+x`, и в рабочей копии тоже `chmod +x` — иначе `git add -A` сбросит бит.
- Установка на сервере одной командой из README:
  `bash <(curl -fsSL https://raw.githubusercontent.com/barakov-dot/tg-proxy-panel-v2/<TAG>/install.sh)`.
  Адрес репозитория и тег задаются переменными в начале install.sh (`REPO_URL`, `REPO_REF`).
  install.sh клонирует репозиторий на этом ref в `/opt/webproxy/src` и ставит всё оттуда.
  update.sh берёт последний тег (или ref из аргумента).

## Обязательные правила (раздел 13 плана)

- Только стандартная библиотека Python. Внешние утилиты на сервере — только из apt, перечисленные в плане.
- `subprocess` только со списком аргументов, никогда `shell=True`. JSON и конфиги не править через sed.
- Никаких секретов, ссылок прокси, URL моста и токенов в логах и выводе, кроме финальной сводки установщика.
- Код tproxy-server и MTProxy не модифицировать.
- Весь пользовательский текст (панель, бот, установщик) на русском. Комментарии и имена в коде — на английском.
- Любая запись конфигурации атомарная. Каждое изменение `profiles.json` и `config.json` relay проходит
  через `-check` с откатом при ошибке.
- Не запускать панель, бота и сервисы от root (кроме `wpp-firewall` oneshot и `wppctl`).
- Не перевыдавать dirty-слоты без смены секрета. Не рестартовать relay вне окна обслуживания без
  явного подтверждения админа. Никаких CDN и внешних ресурсов в панели и заглушке.

## Порядок работы

1. Подготовка (сделано): .gitignore, .gitattributes, README, reference/, коммит `init`.
2. Проверка допущений раздела 14 (сделано): docs/FINDINGS.md, скрипты tools/verify/.
   Если находка ломает архитектуру плана — остановиться, описать проблему и варианты, ждать ответа.
3. Реализация по этапам M1 → M6 (раздел 12 плана), по одному этапу:
   - внутри этапа коммитить логическими частями;
   - в конце этапа: `python3 -m unittest` проходит, `bash -n` проходит для всех .sh, обновлены
     docs/TESTING.md (сценарии проверки на сервере) и раздел «Текущее состояние» ниже;
     коммит `M<N>: <кратко>`, тег `v0.<N>.0`, push ветки и тега;
   - короткий отчёт: что сделано, отклонения от плана и почему, что и какими командами проверить на
     сервере (с учётом тега).

## Субагенты

Использовать субагентов для объёмного чтения и изолированных задач: изучение исходников в
`reference/`, ответы на вопросы по upstream-коду, написание тестов к готовому модулю, проверка кода на
соответствие разделу 13. Субагент возвращает только краткий вывод с путями файлов и номерами строк,
а не содержимое файлов.
