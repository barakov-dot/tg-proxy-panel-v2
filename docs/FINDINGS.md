# Проверка допущений (раздел 14 плана)

Исходники: `reference/tproxy-server` @ `acc252ece3a25c29e9b83f608499a5567a33ab2a`,
`reference/MTProxy` @ `f36d8af769ffaeac36978d38c2c0f6d1104c2137`.
Пути ниже относительно этих каталогов.

Итог: **ничего не ломает архитектуру плана.** Есть уточнения. Главные из них:
`/readyz` нельзя использовать для health, расчёт размера нужно дополнить
`max_pending_items_global`, профилям нужны собственные лимиты на создание потоков.
Всё, что нельзя проверить без сервера, помечено **«проверить на VPS»**.
Для таких пунктов есть скрипты в `tools/verify/`, сценарии описаны в [TESTING.md](TESTING.md).

## 1. MTProxy: 16 секретов, 16 портов, `ss -K`

**16 секретов на процесс — подтверждено.**
`net/net-tcp-rpc-ext-server.c:150-156`: `ext_secret[16][16]` и `assert (ext_secret_cnt < 16)`
перед `ext_secret_cnt++`. 16-й вызов проходит при счётчике 15, 17-й падает на assert.
Шард = 16 слотов, как в плане. При рукопожатии перебираются все секреты
(`:1282`), 16 вычислений SHA-256 на подключение — пренебрежимо мало.

**`-H` с 16 портами — корректно.** `mtproto/mtproto-proxy.c:86` (`MAX_HTTP_LISTEN_PORTS 128`),
разбор `:2148-2166`. Каждый порт должен начинаться с цифры 1–9. Лишние порты сверх 128 дают `usage`.
Для наших 20000–29999 ограничений нет.

**`-S` принимает ровно 32 hex** (`:2195-2225`), без префикса `dd`. В `profiles.json` храним тот же
32-hex секрет. Relay принимает его как 16 байт (`internal/config/config.go:460-482`).

**`--address` использовать нельзя.** Такая опция есть (`engine/engine-net.c:203-211, 244`),
но она привязывает к адресу и **исходящие** сокеты (`net/net-events.c:665-679`), включая соединения
к middle-end Telegram. С `127.0.0.1` MTProxy перестанет работать. Поэтому, как и в плане,
MTProxy слушает `0.0.0.0`, а внешний доступ к 19000–29999 закрывает nft.

**Stats-порт** (`-p`) открывается **только с `--http-stats`**. Без этой опции действует флаг `ENGINE_NO_PORT`,
и порт не слушается вовсе (`mtproto/mtproto-proxy.c:2188-2189, 2364`, `engine/engine.c:623`). Это
подтверждено на VPS. Upstream `deploy/mtproxy.service` эту опцию не передаёт, поэтому `curl :8888/stats`
из upstream README там не работает. В юните шарда передаём `-p <19000+N> --http-stats`. Ответ на `/stats`
даётся только клиенту `127.0.0.1` (`mtproto/mtproto-proxy.c:1394`). Порт слушает `0.0.0.0`, внешний
доступ закрывает nft. Здоровье шарда проверяем через `GET http://127.0.0.1:<19000+N>/stats` (см. п. 2).

**`ss -K`** — подтверждено на VPS (`tools/verify/nft-ss.sh`, Ubuntu 24.04). Нужны ядро с `CONFIG_INET_DIAG_DESTROY=y`
и `CAP_NET_ADMIN`, то есть вызов через `wppctl`. Убивать нужно обе стороны:
`ss -K -tn state established '( sport = :P or dport = :P )'`.
Когда relay теряет backend-сокет, `readLoop` завершается, поток закрывается и клиенту уходит
`CLOSE` (`internal/session/session.go:1498-1573`).

## 2. Relay: отказ backend одного профиля и `/readyz`

**Отказ `connect` даёт только `CLOSE` потока.** Сессия остаётся жива. Код:
`internal/session/session.go:1502-1506` (dial с ошибкой → `backendClosed`); upstream `PLAN.md:508`
(«dial failure → enqueue CLOSE; keep the relay session alive»).

**`/readyz` проверяет ВСЕ backend-ы.** `internal/server/server.go:679-695`: последовательный
`DialTimeout` к каждому профилю, при первой ошибке 503. У нас свободные и выключенные слоты
заблокированы reject-ом, поэтому `/readyz` будет **всегда 503**. Кроме того, каждый вызов
открывает до 1000 соединений к шардам.

**Решение (уточнение плана):**
- health relay = только `/healthz` (живость процесса);
- health шарда = `systemctl is-active wpp-mtproxy@N` + `GET /stats` на stats-порту шарда;
- после рестарта (окно обслуживания, `update --core`, откат) ждём `/healthz` и `/stats` всех шардов;
  `/readyz` не вызываем нигде (в том числе ради счётчиков трафика).

## 3. Relay: резерв на сессию против `max_pending_*`

`internal/session/session.go:1157-1183` (`ValidateBudget`, `pendingControlReserve`), константы `:19-23`,
`frame.HeaderSize = 8`:

```
reserve_items = 16 + 3 × max_streams_per_session          (глобальное значение, по умолчанию 128 → 400)
reserve_cost  = reserve_items × (256 + 8 + 4)             (по умолчанию 107 200 байт ≈ 105 КиБ)
-check падает, если reserve_cost  > max_pending_global       // max_sessions_global
                  или reserve_items > max_pending_items_global // max_sessions_global
```

Проверка вызывается и при `-check`, и при старте (`cmd/tproxy-server/main.go:31`, `internal/server/server.go:57`).

**Важная поправка к разделу 9 плана.** Первым упирается `max_pending_items_global`, а не
память: при дефолтных 262 144 элементах предел — **655 сессий**. При 300 пользователях × 2 = 600
сессий `-check` проходит, но для данных остаётся всего ~22 тыс. элементов (из-за этого скорость
упрётся в лимит). Элементы — это счётчик, память ограничивается байтовым бюджетом. Формулы для
`sizing.py`:

```
S  = max_streams_per_session (128)
Ri = 16 + 3·S;  Rc = Ri · 268
max_pending_global       = min(512 MiB, 25% RAM); требуется sessions · Rc ≤ 50% от него,
                           иначе уменьшать max_sessions_global и предупреждать
max_pending_items_global = sessions · Ri + 262144
```

Прочие проверки `validate()` (`internal/config/config.go:320-353`): глобальные лимиты не меньше
per-session (`max_pending_global ≥ max_pending_per_session` = 32 МиБ и т. п.),
`max_streams_global ≥ max_backend_dials_in_flight`. Граница — проверить на VPS
(`tools/verify/relay-check.sh` сверяет её с реальным `-check`).

**Лимиты на создание сессий и потоков надо масштабировать.** После рестарта relay все клиенты
переподключаются одновременно, а дефолтные ведра рассчитаны на 128 сессий:
`new_sessions_burst` 128 (600/мин), `new_streams_burst` 512 (6000/мин),
`new_bootstraps_burst` 256 (1200/мин) (`config.go:219-226`). Отказ — 503 `Retry-After: 1`,
клиент повторяет, то есть это не поломка, а растянутое восстановление. В `sizing.py`:
`new_sessions_burst = max(128, sessions)`, `new_bootstraps_burst = max(256, 2·sessions)`,
`new_streams_burst = max(512, 4·sessions)`, в минуту — ×5 от burst. Окончательные значения — после
замеров M6.

Прочее: `max_profiles` проверяется на старте (`config.go:546`), верхней границы нет — подтверждено.

## 4. Per-profile `limits.max_sessions` как «макс. устройств»

`internal/session/manager.go:212-220`: новая сессия отклоняется (503 `Retry-After: 1`), если у
профиля уже `max_sessions` **живых** сессий. Одна сессия = один WebView-транспорт одного приложения,
то есть примерно одно устройство.

Оговорки:
- сессия, чей клиент пропал без `DELETE` (сон телефона, смена сети), считается ещё до
  `reconnect_grace` = 2 мин (`manager.go:603-624`). При лимите «2» человек со сменой сети может
  на пару минут получить отказ;
- Android держит WebView только на переднем плане (`ANDROID.md`), сворачивание ⇒ новая сессия.

**Решение владельца (изменение плана):** одна ссылка = одно устройство, `limits.max_sessions = 1`
у каждого профиля; у человека может быть несколько устройств (слотов), лимит устройств на человека,
по умолчанию 1. PLAN.md обновлён (разделы 0, 2, 4, 5, 8, 9, 12).

Следствие оговорки выше: при лимите 1 «осиротевшая» сессия блокирует устройство до истечения
`reconnect_grace`. Поэтому в `config.json` relay задаём `timeouts.reconnect_grace = "60s"` вместо 2 мин.
Живой мост обновляет сессию каждым long poll (25 с), а десктоп сбрасывает соединения после 30–45 с
тишины (upstream `README.md:565-573`). Отказ по лимиту — 503 `Retry-After: 1`, мост повторяет.
**Проверить на VPS в M1** с реальными клиентами: сворачивание/разворачивание Android, смена сети,
перезапуск приложения — сколько секунд устройство ждёт повторного подключения; второе устройство
с той же ссылкой должно получать отказ. По результату значение уточняется (30–90 с).
`max_sessions_global = pool_slots` (у каждого слота ≤ 1 сессии).
Проверить на VPS: `tools/verify/relay-check.sh` (3-я сессия при лимите 2 → 503, после `DELETE` — снова ок).

## 5. nft: именованные счётчики через map

Синтаксис `counter name tcp dport map @cnt_up` с `map cnt_up { type inet_service : counter; }`
(objref-map) существует в nftables с 0.9.x, поэтому на 1.0.2 и 1.0.6 должен работать —
**проверить на VPS** (`tools/verify/nft-ss.sh` проверяет плановую таблицу и запасной вариант
«правило на порт»). Там же проверяется:
- каждое направление считается один раз: up — в `output` по `dport` (relay→MTProxy), down — в `input`
  по `sport` (MTProxy→relay). Пакет по loopback проходит и output, и input, но каждое правило
  ловит только своё направление;
- `reject with tcp reset` в `output` сразу даёт `ECONNREFUSED` новому подключению;
- счётчики и элементы map можно добавлять в живую таблицу (расширение пула без пересоздания).

Уточнения:
- **Чтение счётчиков требует root** (netlink nftables нужен `CAP_NET_ADMIN`). В `wppctl` добавляется
  подкоманда `counters` (печатает JSON `{port: [up, down]}`), а воркер вызывает её через sudo.
  План это допускает («или через `wppctl`»).
- Для новых шардов нужны объекты-счётчики и элементы map: `wppctl` получает подкоманду
  `sync`, которая идемпотентно пересоздаёт `table inet wpp` из БД (её же вызывает `wpp-firewall.service`).
  `install-shard-unit <N>` вызывает её после добавления шарда.
- `nft delete element` отсутствующего элемента — ошибка. `destroy element` появился только в
  nftables 1.0.8, на 1.0.2/1.0.6 его нет. `wppctl unblock` сначала читает `@blocked` и удаляет
  только присутствующие порты.
- Счётчики считают IP-байты вместе с заголовками TCP/IP; readyz мы не вызываем (п. 2).
  Подпись в UI «≈ трафик Telegram» остаётся верной.

## 6. Сессия, у которой все потоки получают `CLOSE`

Со стороны relay (код): сессия **не закрывается** (п. 2), `new_sessions_per_minute` не
расходуется. Клиент будет заново открывать потоки, и каждый `OPEN` сначала берёт жетон из ведра
создания потоков профиля и **глобального** ведра (`manager.go:405-434`), затем dial получает отказ.

Найдена опасность: несколько выключенных пользователей с открытым Telegram могут выбрать
глобальное ведро `new_streams_per_minute` и мешать остальным. Защита уже есть в коде:
`allowProfileRateLocked` (`manager.go:552-577`) не списывает жетоны, если отказал хотя бы один
уровень. Поэтому **для каждого профиля задаём собственные `new_streams_per_minute` /
`new_streams_burst`** (стартовые значения 300/мин и 64, уточнить в M6). Тогда выключенный клиент
расходует глобальное ведро не быстрее своего лимита. Проверить на VPS: `tools/verify/relay-check.sh`
(отказы профиля не расходуют глобальный запас).

Отдельно: выключенный клиент держит живую сессию и занимает место в `max_sessions_global`.
Это учтено: `max_sessions_global = pool_slots`, то есть по сессии на каждый слот, включая выключенные.

Реальный клиент Telegram (частота переподключений, не пересоздаёт ли он WebView-сессию) —
**проверить на VPS** в M1 с настоящим клиентом: `tools/verify/client-reconnect-watch.sh`.
Если клиент зацикливается в создании сессий, вариант из плана: не reject, а оставить порт
открытым — решим по результату.

## Прочие находки и уточнения

7. **`-u` без root ничего не делает** — подтверждено: `common/server-functions.c:115-118`
   (`change_user` действует только при `getuid()==0`), вызов в `engine/engine.c:213-216`.
   Шарды запускаются сразу от `webproxy`; `-u` не передаём. Лимит файлов: без root MTProxy
   урезает `maxconn` до `RLIMIT_NOFILE − 16` (`engine/engine.c:176-194`), поэтому `LimitNOFILE=1048576`
   в юните обязателен. `-C` — лимит подключений на воркер (с `-M 1` — один воркер).
8. **RSS шарда и `-M 0`** — замерено на VPS (Ubuntu 24.04, простой, 16 секретов): `-M 1` (родитель +
   воркер) — **15,1 МиБ**, `-M 0` (один процесс) — **8,2 МиБ**; оба варианта слушают все 16 портов.
   При 63 шардах (1000 пользователей) разница ~430 МиБ. **Решение: шарды запускаются с `-M 0`.**
   Под нагрузкой это тоже один цикл обработки клиентов, как и один воркер при `-M 1`. Поведение под
   нагрузкой и RSS в работе перепроверяются в M6.
9. **Права на `profiles.json`:** без systemd-credential relay требует отсутствия битов group/other
   (`internal/config/config.go:517-527`). Файл пишет `webproxy`, relay запускается от `webproxy` →
   `0600` и прямой путь в `profiles_file`, без `LoadCredential`. `token.key`: 32 байта, `0600`/`0400`,
   без group/other (`internal/config/token_key.go:22-27`). `-check` читает ключ и `public_dir`
   (`internal/server/server.go:52-58`), поэтому запускать `-check` нужно от `webproxy`.
10. **Конфиг relay строгий:** `DisallowUnknownFields` для `config.json` и `profiles.json`
    (`config.go:247-253, 538-545`). Генерируем только известные поля. Имя профиля — 1–64 символа
    (`s000-00` подходит). Дубликат секрета внутри хоста даёт одинаковую capability и отказ (`config.go:578`).
11. **Сайт-заглушка:** relay обслуживает `public_dir` сам (читает при старте, нужен `index.html`,
    `static_routes: "exact"`, рекомендуется `404.html`). Изменение заглушки = рестарт relay.
12. **Маршрут панели в обход relay.** Upstream рекомендует пускать через relay все пути
    (`README.md:435-439`, `PUBLIC_SITE.md`). План направляет `/<panel_path>/*` мимо relay — это
    осознанное решение плана (Mode B для одного префикса). Путь знает только админ, у остальных
    запросов стек ответа одинаковый. Оставляем как есть.
13. **Исходящие MTProxy:** адреса middle-end берутся из `proxy-multi.conf` и меняются. Статический
    `IPAddressAllow` для MTProxy ненадёжен, поэтому у шардов `IPAddressDeny` не задаём (как в
    upstream `deploy/mtproxy.service`). Loopback-порты защищены nft.
14. **`carrier_mode`:** план не задаёт режим. Опускаем поле, relay берёт `https` (дефолт upstream,
    `config.go:51-56`). Режим на пользователя — в «На будущее».
15. **Проверка входа relay:** `MatchCapability` линейно сравнивает все профили за константное время
    (`manager.go:126-141`). Для 1000 профилей это дёшево, замер в M6.
16. **Проверенные бинарники:** Caddy 2.11.4 (SHA-512) и Go 1.26.5 (SHA-256) — значения из upstream
    `deploy/install.sh:127-128, 161-162`. MTProxy — архив с SHA-256 из `deploy/install-mtproxy.sh:22-23`.
    SHA-256 архива tproxy-server `acc252ece3a25c29e9b83f608499a5567a33ab2a` (GitHub archive `.tar.gz`),
    получен на VPS: `4db6003ac7f06aa8b1e179249b470c4b0d8db3a62cf5152d1cabc86bf3c7197b`. Закрепляем в `install.sh` (M5).
